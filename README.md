# Выездной инженер

Мобильное приложение выездного инженера сервисной службы (Android) и сервер «Сервисный пульт»
(ASP.NET Core 8, PostgreSQL).

## Состав

- `android/` — приложение: Kotlin, Jetpack Compose, Room, Retrofit + OkHttp, WorkManager,
  ручной контейнер зависимостей.
- `server/` — сервер «Сервисный пульт»: `ServicePult` (Web API, Razor Pages, EF Core + Npgsql,
  Serilog) и `ServicePult.Tests` (xUnit: расчёт сроков SLA, отчёт по SLA, регистрация заявок,
  интеграционные тесты API и страниц пульта).
- `tools/make_seed.py` — генератор тестовых данных (справочники, заявки со сроками SLA,
  производственный календарь 2026–2027); с инкремента И6 их загружает сервер.
  `tools/make_qr.py` — QR-метки тестового оборудования для проверки сканера (`tools/qr/`).
- `screenshots/` — снимки экранов.

## Требования

- JDK 17 или новее (проверено на JDK 21) и Android SDK с платформой 37 — для приложения;
- .NET SDK 8 — для сервера;
- PostgreSQL 18 (проверено на 18.6; подойдёт и служба Windows, и переносная сборка без установки);
- Python 3 — для генераторов в `tools/` (для `make_qr.py` — ещё библиотеки `qrcode` и `pillow`).

## Сборка

Нужны JDK 17 или новее и Android SDK с платформой 37 (`platforms;android-37.0`).
Путь к SDK — в `android/local.properties` (`sdk.dir=...`), файл в репозиторий не входит.

```
cd android
gradlew assembleDebug          # APK: app/build/outputs/apk/debug/app-debug.apk
gradlew testDebugUnitTest      # модульные тесты
gradlew lintDebug              # Android Lint
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

Отладочная сборка ходит на сервер по `http://10.0.2.2:5080/` (подробнее — в разделе
«Приложение и сервер»), поэтому сначала нужно запустить сервер.

Путь проекта содержит кириллицу, поэтому в `gradle.properties` включён
`android.overridePathCheck=true`.

## Сервер «Сервисный пульт»

Нужны .NET SDK 8 и PostgreSQL 16–18. Для разработки используется переносной PostgreSQL 18
из папки `_tools` рядом с `приложение_код`: запуск — `_tools\pg_start.cmd` (слушает
`localhost:55433`), остановка — `_tools\pg_stop.cmd`. Базы `servicepult` (рабочая) и
`servicepult_tests` (для интеграционных тестов), владелец обеих — пользователь `servicepult`.

**Создание базы** (один раз; `psql` под суперпользователем `postgres`, для переносного —
`psql -h localhost -p 55433 -U postgres`):

```sql
CREATE ROLE servicepult LOGIN PASSWORD '<пароль>';
CREATE DATABASE servicepult OWNER servicepult;
CREATE DATABASE servicepult_tests OWNER servicepult;
```

Таблицы создавать не нужно — их создают миграции при первом запуске сервера (и тесты — в
`servicepult_tests`).

**Настройки, которых нет в репозитории.** Пароли и ключи в git не попадают: файлы
`appsettings.Development.json` перечислены в `.gitignore` (и в корневом, и в `server/.gitignore`).
Перед первым запуском скопируйте образец `server/ServicePult/appsettings.Development.example.json`
в `server/ServicePult/appsettings.Development.json` и впишите пароль и ключ вместо заглушек:

```json
{
  "ConnectionStrings": {
    "Default": "Host=localhost;Port=55433;Database=servicepult;Username=servicepult;Password=<пароль>"
  },
  "Jwt": {
    "Key": "<случайная строка не короче 32 байт>"
  }
}
```

Ключ подписи токенов можно получить, например, так:
`python -c "import secrets; print(secrets.token_urlsafe(48))"` или в PowerShell
`[Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(48))`. Без `Jwt:Key` сервер не
запускается и пишет, чего не хватает. Те же настройки можно задать переменными окружения
`ConnectionStrings__Default` и `Jwt__Key` (так их задают в эксплуатации).

Для интеграционных тестов — `server/ServicePult.Tests/appsettings.Development.json`
(образец — `appsettings.Development.example.json` рядом):

```json
{
  "ConnectionStrings": {
    "Tests": "Host=localhost;Port=55433;Database=servicepult_tests;Username=servicepult;Password=<пароль>"
  }
}
```

или переменная окружения `ConnectionStrings__Tests`. Без неё интеграционные тесты
пропускаются с сообщением, тесты расчёта сроков SLA выполняются всегда. Тестовая база перед
каждым прогоном очищается и заполняется заново.

**Сборка, тесты, запуск:**

```
cd server
dotnet tool restore            # dotnet-ef из server/.config/dotnet-tools.json
dotnet build
dotnet test
cd ServicePult
dotnet run                     # http://localhost:5080, окружение Development
```

`dotnet run` берёт адрес и окружение из `Properties/launchSettings.json`. То же без профиля
запуска (так удобнее, если адрес нужно сменить):

```
set ASPNETCORE_ENVIRONMENT=Development
dotnet run --no-launch-profile --urls http://localhost:5080
```

Запущенный сервер держит сборки в `bin/` — перед `dotnet build` и `dotnet test` его нужно
остановить.

При старте сервер применяет миграции EF Core (`Data/Migrations`) и, если таблица `employee`
пуста, загружает тестовые данные `ServicePult/SeedData/seed.json` (при сборке файл копируется
в папку вывода, сервер читает копию оттуда). Новая миграция после
изменения сущностей: `dotnet tool restore`, затем
`dotnet ef migrations add <Имя> --project ServicePult --output-dir Data/Migrations` (из папки
`server`).

Где что лежит:

- `Data/` — 14 сущностей (имена таблиц и столбцов как в проекте системы) и `AppDbContext`
  (ставит `updated_at` при каждом сохранении);
- `Services/SlaService.cs` — расчёт сроков SLA (тот же алгоритм, что `SlaCalculator` в
  приложении), `PushService.cs` — проверки приёма данных с телефона;
- `Controllers/` — API: `/api/auth/login`, `/api/auth/refresh`, `/api/sync/pull`,
  `/api/sync/push`, `/api/files`;
- `Pages/` — страницы пульта диспетчера (Razor Pages);
- `App_Data/files/` — файлы с телефонов (фото, подписи, акты PDF), `logs/` — журнал сервера
  по дням (`servicepult-ГГГГММДД.log`), события безопасности помечены `[Безопасность]`.
  Обе папки не входят в репозиторий.

В эксплуатации (окружение Production) сервер работает только по HTTPS (перенаправление и HSTS);
порядок развёртывания — в разделе «Развёртывание в эксплуатации».

Тестовые учётные записи (пароль у всех `Test2026!`):

| Логин | Роль | Куда пускают |
|---|---|---|
| `engineer` | инженер | мобильное приложение |
| `dispatcher` | диспетчер | страницы пульта |
| `head` | руководитель службы | страницы пульта, отчёты |

После 5 неверных паролей подряд вход по логину закрывается на 15 минут.

### Страницы пульта

Открываются в браузере на том же адресе (`http://localhost:5080` в отладке). Вход — по логину и
паролю на странице `/Account/Login`, сеанс хранится в cookie (8 часов, продлевается при работе).
API приложения cookie не принимает, а страницы — токен JWT: у них разные схемы входа. Счётчик
неудачных входов общий с API. Инженеров на пульт не пускают; если сотрудника заблокировать или
сменить ему роль, открытый сеанс пульта прекращается при следующем запросе.

| Адрес | Страница | Кто |
|---|---|---|
| `/Dispatcher` | В1 «Пульт диспетчера» (главная): заявки со сроком, остатком и признаком «в срок / под угрозой / просрочена», фильтры, обновление раз в минуту | диспетчер, руководитель |
| `/Dispatcher/New` | «Новая заявка»: сроки SLA и номер `З-ГГММ-NNNN` назначаются при сохранении | диспетчер, руководитель |
| `/Dispatcher/Request/{id}` | карточка заявки: назначение и переназначение инженера, отмена с причиной (только в статусах «Новая» и «Назначена») | диспетчер, руководитель |
| `/Reports/Sla` | В2 «Отчёт по SLA» за период (по умолчанию — текущий месяц), по уровням SLA и заказчикам, загрузка инженеров | руководитель |
| `/Directories/Customers`, `/Sites`, `/Equipment` | справочники заказчиков (с договорами), объектов и оборудования — просмотр | диспетчер, руководитель |
| `/Directories/Calendar` | производственный календарь: дни-исключения, добавление и удаление | диспетчер, руководитель |

Регистрация, назначение и отмена заявок — `Services/RequestService.cs`, расчёт отчёта —
`Services/ReportService.cs`, вход на пульт — `Services/PultAuth.cs` и `Pages/Account/`. Действия с
заявками пишутся в журнал сервера с пометкой `[Заявка]`, изменения календаря — `[Справочник]`,
входы на пульт — `[Безопасность]`. Оформление страниц — `wwwroot/css/site.css`, внешние
библиотеки и шрифты не используются.

## Приложение и сервер

С инкремента И6 единственный источник данных приложения — сервер «Сервисный пульт».
Тестовых данных внутри приложения больше нет: **без сервера войти нельзя** (на экране входа
будет «Нет связи с сервером»).

Адрес сервера задаётся при сборке (`BuildConfig.API_BASE_URL`, файл `android/app/build.gradle.kts`):

- **debug** — `http://10.0.2.2:5080/`. Адрес 10.0.2.2 эмулятор Android видит как `localhost`
  компьютера, поэтому сервер нужно запустить на том же компьютере на порту 5080. Открытый HTTP
  разрешён только к этому адресу и только в debug-сборке
  (`android/app/src/debug/res/xml/network_security_config.xml`).
- **release** — `https://pult.example.invalid/`. Это заглушка (домен `.invalid` не существует):
  при внедрении сюда подставляется настоящий адрес сервера. В рабочей сборке открытый HTTP
  запрещён, только HTTPS.

Как работает обмен:

- Вход — `POST /api/auth/login`; токены доступа и обновления хранятся в телефоне
  зашифрованными ключом Android Keystore (AES-GCM). Когда токен доступа истекает, приложение
  само обновляет его; если сервер отказал в обновлении (учётная запись заблокирована), приложение
  выходит и очищает данные.
- Все действия инженера сначала пишутся в локальную базу (sync_state = 1), а фоновая
  синхронизация WorkManager отправляет их, когда есть сеть: после каждого изменения, раз в
  15 минут и по кнопке «Синхронизировать сейчас» на экране «Синхронизация» (Э10).
  Порядок обмена: файлы (фото, подписи, акты PDF) → push → pull.
- «Выйти» — на экране Э10: удаляются токены, база, файлы и опорная пара доверенного времени.

## Защита данных в приложении

- **Блокировка (экран Э0).** После 5 минут без касаний экрана, а также при возврате из фона,
  если с последнего действия прошло 5 минут, поверх текущего экрана открывается «Разблокировка».
  Время считается по монотонным часам (перевод часов телефона не помогает). Момент последнего
  действия сохраняется при сворачивании: если система выгрузила приложение, отсчёт продолжается;
  после перезагрузки телефона приложение сразу заблокировано. После разблокировки инженер
  остаётся на том же экране с введёнными данными.
- **Чем разблокировать.** PIN инженера — тот же, которым подтверждается подпись акта. PIN
  задаётся сразу после каждого входа по паролю (шаг «Задайте PIN», дважды; до него в приложение
  не пускает) — так же сбрасывается забытый PIN. На Э0 и при подписи PIN не создаётся: если его
  нет, сеанс блокируется и нужен вход по паролю. Отпечаток — системный BiometricPrompt, только
  биометрия класса 3 (`BIOMETRIC_STRONG`), Android 9 и новее. Код блокировки телефона
  (`DEVICE_CREDENTIAL`) не принимается: его могут знать другие люди, а Э0 должен подтвердить
  именно инженера.
- **5 неверных PIN** (общий счётчик с подписью акта) или кнопка «Войти по паролю» —
  сеанс блокируется: токены удаляются, фоновый обмен останавливается, открывается экран входа.
  База и файлы **не** удаляются: после входа того же сотрудника по паролю неотправленные записи
  уйдут на сервер. Вход другим сотрудником, как и прежде, очищает данные телефона. Полный выход
  с удалением всего — кнопка «Выйти» на Э10.
- **Хеш PIN.** В настройках хранится соль и HMAC-SHA256(ключ Android Keystore, PBKDF2(PIN, соль)).
  Ключ HMAC неэкспортируемый, поэтому по украденному файлу настроек PIN из 4–6 цифр не перебрать
  на компьютере. Записи старого формата (только PBKDF2) проверяются как раньше и при первом
  верном PIN пересохраняются в новом — задавать PIN заново не нужно.
- **Запрет снимков экрана (FLAG_SECURE)** на экранах с персональными данными: Э0, Э3 (контакт
  заказчика), Э7 (подпись), Э8 (акт). На них нельзя сделать скриншот или запись экрана, в списке
  недавних приложений вместо содержимого — пустое окно. Флаг управляется полем
  `BuildConfig.SECURE_SCREENS`: в release — всегда `true`; в debug по умолчанию `false`, чтобы
  снимать скриншоты с эмулятора для документации. Проверить защиту в отладочной сборке:
  `gradlew assembleDebug -PsecureScreens=true`.
- **Резервные копии.** `allowBackup="false"`, а `data_extraction_rules.xml` (Android 12+) и
  `backup_rules.xml` (Android 8–11) исключают все области хранения — база, файлы и настройки
  (токены, хеш PIN) не попадают ни в облачную копию, ни в перенос на новый телефон. Ключи
  Keystore система не копирует в любом случае.
- **Шифрование локальной базы (SQLCipher)** — этап развития, пока не сделано: база лежит во
  внутреннем хранилище приложения, которое Android шифрует вместе с разделом данных.

## Тестовые данные

Все организации, адреса, люди и телефоны вымышленные. Пересобрать данные:

```
python tools/make_seed.py                  # база — последняя прошедшая пятница
python tools/make_seed.py --база 2026-10-02
python tools/make_seed.py --база 2026-10-02 --съёмка 2026-10-05
```

`--база` — пятница, в 16:30 которой зарегистрирована контрольная заявка З-ГГММ-0137 (SLA-2).
`--съёмка` — день съёмки экранов: «сегодняшние» заявки 6 и 7 с открытыми интервалами
переносятся на утро этого дня, чтобы в показателях не набегали десятки часов от пятницы
(без ключа день съёмки совпадает с базой).
Кроме заявок, генератор пишет интервалы времени и отметки чек-листа по уже начатым и
закрытым заявкам.
Тестовые данные загружает сервер; в приложение они попадают при входе (полная загрузка).
Генератор пишет `server/ServicePult/SeedData/seed.json`; сервер заливает его только в пустую
базу (таблица `employee` без записей), поэтому новые данные попадут в уже заполненную базу
лишь после её очистки. Порядок пересоздания:

1. остановить сервер;
2. `python tools/make_seed.py ...` с нужными ключами;
3. пересоздать базу (`psql -h localhost -p 55433 -U postgres`):
   `DROP DATABASE servicepult;` и `CREATE DATABASE servicepult OWNER servicepult;`;
4. запустить сервер (`dotnet run`) — миграции создадут таблицы, данные зальются из нового файла;
5. в телефоне — «Выйти» на экране Э10 (или `adb shell pm clear ru.fieldengineer.app`) и войти
   заново: приложение выполнит полную загрузку.

QR-метки тестового оборудования для проверки сканера (нужна библиотека `qrcode`):

```
python tools/make_qr.py        # tools/qr/BK-EQ-000123.png и т. д.
```

Готовые метки для оборудования из текущих тестовых данных уже лежат в `tools/qr/`.

В эмуляторе метку можно повесить на стену виртуальной сцены камеры:
`emulator -avd <AVD> -camera-back virtualscene -virtualscene-poster wall=<путь к PNG>`;
повернуть камеру к стене — в окне эмулятора, удерживая Alt и двигая мышью (или клавишами WASD).

Учётная запись инженера: логин `engineer`, пароль `Test2026!` (проверяет сервер, в телефоне
пароль и его хеш не хранятся). PIN для подписи актов и разблокировки задаётся сразу после
каждого входа по паролю (в проверках использовался 4071; «1234», «1111» отклоняются как простые).
Диспетчер (`dispatcher`) и руководитель (`head`) входят только на страницы пульта — в
приложение их не пускают (ответ 403).

## Развёртывание в эксплуатации

1. **База.** PostgreSQL 18 на сервере организации: роль и база `servicepult` — как в разделе
   «Создание базы», с надёжным паролем. Тестовую базу `servicepult_tests` в эксплуатации не
   создают. Внимание: при первом запуске в пустую базу заливается `SeedData/seed.json`, а в
   нём тестовые учётные записи с паролем `Test2026!` — перед вводом в работу файл заменяют
   настоящими справочниками и учётными записями.
2. **Публикация сервера:** `dotnet publish server/ServicePult -c Release -o <папка>`; в папке
   публикации сервер создаёт `logs/` и `App_Data/files/` — у учётной записи службы должны быть
   права на запись в них.
3. **Окружение и секреты.** `ASPNETCORE_ENVIRONMENT=Production`; строка подключения и ключ
   подписи токенов — только переменными окружения `ConnectionStrings__Default` и `Jwt__Key`
   (ключ — своя случайная строка не короче 32 байт, не тот, что при разработке). В
   `appsettings.json` пароля и ключа нет и быть не должно. Папку для файлов можно вынести
   настройкой `Files__Root` (по умолчанию `App_Data/files` относительно папки сервера).
4. **HTTPS.** В окружении Production сервер перенаправляет HTTP на HTTPS и отдаёт HSTS.
   Варианты: IIS с модулем ASP.NET Core (сертификат — в привязке сайта); nginx как обратный
   прокси с TLS — тогда серверу нужна переменная `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true`,
   чтобы он видел исходную схему HTTPS (в `Program.cs` обработка заголовков прокси отдельно не
   включена); либо Kestrel напрямую с сертификатом (`Kestrel__Certificates__Default__Path` и
   `Kestrel__Certificates__Default__Password`, адрес — `ASPNETCORE_URLS=https://+:443`).
5. **Резервное копирование:** база — `pg_dump -Fc servicepult > servicepult_ГГГГММДД.dump`
   по расписанию; вместе с ней — папка `App_Data/files/` (фото, подписи, акты PDF: в базе
   только ссылки и контрольные суммы). Журнал `logs/` хранится 90 дней, старые файлы сервер
   удаляет сам.
6. **Приложение.** В `android/app/build.gradle.kts` (тип сборки `release`, поле
   `API_BASE_URL`) заглушку `https://pult.example.invalid/` заменить на адрес сервера; собрать
   `gradlew assembleRelease` и подписать APK ключом организации (хранилище ключей — вне
   репозитория). Подпись в `build.gradle.kts` не настроена — её добавляют при внедрении
   (`signingConfigs`) или подписывают готовый APK утилитой `apksigner` из Android SDK.
7. **Проверка после развёртывания:** вход на пульт по HTTPS, регистрация заявки, её получение
   в телефоне и возврат закрытой с актом; в журнале сервера нет ошибок.
